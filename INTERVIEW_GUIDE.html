Architecture Core
1. Explain LedgerOne's 3-tier multi-module architecture. Why are feature-to-feature dependencies strictly forbidden?

LedgerOne decomposes the application into three decoupled tiers:

  • :app (Application Shell): Wires Hilt dependency injection graphs, top-level navigation (LedgerNavHost), and background work dispatchers (WorkManager).
  • :feature:* (Feature Libraries): Encapsulates UI screens and ViewModels for distinct product domains (e.g., :feature:home, :feature:history, :feature:auth, :feature:account).
  • :core:* (Core Shared Layer): Reusable domain models, design system, network abstractions, Room database, and testing utilities (e.g., :core:model, :core:designsystem, :core:database, :core:network).
Why forbid feature-to-feature dependencies? Allowing :feature:wallet to import :feature:ledger creates circular dependencies, tight coupling, and massive Gradle build bottlenecks. If two features need the same model, repository, or UI primitive, that code must be elevated to :core:*. This invariant is automatically verified by ModuleBoundaryTest on every CI build.
Architecture Advanced
2. What are standalone feature demo apps (`:feature::demo`), and what technical problem do they solve?

Every feature module has a runnable companion application (e.g., :feature:home:demo, :feature:auth:demo). Feature libraries (com.android.library) cannot be launched as standalone APKs on devices. The demo app is a minimal com.android.application that embeds only that feature and mocks.

  • Instant Build Times: Building :app takes 30–60s due to full Room annotation processing, Hilt compilation, and all feature assets. Running :feature:account:demo compiles in 1–3 seconds.
  • Zero Navigational Friction: Developers and QA test deep edge cases (e.g., OTP timeouts, KYC rejection) immediately without logging in or navigating through the entire app funnel.
  • Independent Team Scalability: Feature teams can iterate without being blocked by regressions or merge conflicts in unrelated features.
Coroutines Deep Dive
3. Why must you NEVER swallow `CancellationException` in Kotlin coroutines? How can standard `runCatching` cause leaks?

In Kotlin, structured concurrency cancellation is cooperative and implemented under the hood by throwing CancellationException. When a coroutine scope cancels (e.g., user exits screen and viewModelScope terminates), a CancellationException cascades through the coroutine hierarchy.

The Danger of Swallowing CancellationException: If you catch Exception or Throwable without rethrowing CancellationException, the coroutine ignores the cancellation signal and continues running wasted work, leaking CPU cycles and network memory in the background! 
// ❌ INCORRECT: Swallows cancellation, preventing coroutine termination
try {
    api.submitTransfer(payload)
} catch (e: Exception) {
    Log.e(TAG, "Failed", e)
}

// ✅ CORRECT: Explicitly rethrows CancellationException
try {
    api.submitTransfer(payload)
} catch (e: CancellationException) {
    throw e
} catch (e: IOException) {
    Result.failure(e)
}

// ✅ CORRECT: runCatching with cancellation propagation
val result = runCatching { api.fetchStatement() }
    .onFailure { if (it is CancellationException) throw it }
Coroutines Core
4. Why should ViewModels expose read-only `StateFlow` via `WhileSubscribed(5_000)` instead of `Eagerly` or LiveData?

Converting upstream cold flows (e.g., Room database queries or location updates) into hot UI state in ViewModels is accomplished using stateIn:

val uiState: StateFlow<HomeUiState> = repository.observeDashboard()
    .map { HomeUiState.Success(it) }
    .stateIn(
        scope = viewModelScope,
        started = SharingStarted.WhileSubscribed(5_000),
        initialValue = HomeUiState.Loading
    )
  • Why `WhileSubscribed`? When the composable leaves the screen, upstream database/network flows automatically stop collecting, preserving battery and memory.
  • Why the 5,000ms (5-second) buffer? During configuration changes (screen rotation, multi-window split, dark mode toggle), the Activity destroys and recreates within ~200–500ms. The 5-second grace window keeps the upstream flow alive, avoiding expensive database restarts and screen flickering!
Financial Math Core
5. Why are currency amounts stored strictly as 64-bit `Long` minor units instead of `Double` or `Float`?

Floating-point types (Float and Double) adhere to the IEEE 754 binary standard, which represents fractions in base 2. Most decimal fractions (such as 0.10 or 0.01) cannot be represented precisely in binary:

// In Java/Kotlin:
println(0.1 + 0.2) // Prints: 0.30000000000000004!
The LedgerOne Rule: In financial software, a fraction of a cent discrepancy will fail bank reconciliations and audit compliance. LedgerOne stores all currency as integer Long values in **minor units** (paise for INR, cents for USD). Example: ₹1,245.50 is stored strictly as 124550L.
Financial Math Advanced
6. How does double-entry bookkeeping work in LedgerOne, and what invariants are enforced by `post()`?

Double-entry bookkeeping mandates that money never appears from or disappears into thin air; every debit from one account must be matched by an identical credit to another account:

fun post(legs: List<LedgerLeg>): Boolean {
    require(legs.isNotEmpty()) { "Transaction must contain at least one leg" }
    
    // Invariant 1: Every leg must be either debit or credit, never both or negative
    legs.forEach { leg ->
        require(leg.debitMinor >= 0L && leg.creditMinor >= 0L)
        require((leg.debitMinor == 0L) xor (leg.creditMinor == 0L))
    }
    
    // Invariant 2: Total debits must equal total credits
    val totalDebits = legs.sumOf { it.debitMinor }
    val totalCredits = legs.sumOf { it.creditMinor }
    return totalDebits == totalCredits
}
Financial Math Advanced
7. How does remainder-preserving expense splitting (`splitEvenly`) guarantee zero currency leakage?

When dividing ₹100.00 (10,000 paise) among 3 people, integer division yields 10000 / 3 = 3333 paise per person ($3333 \times 3 = 9999$). One paisa is lost as remainder! Ordinary systems drop the remainder or round up, causing financial drift.

splitEvenly solves this by distributing remainder paise one-by-one to the earliest participants:

fun splitEvenly(totalMinor: Long, parts: Int): List<Long> {
    require(parts > 0)
    val base = totalMinor / parts
    val remainder = (totalMinor % parts).toInt()
    
    return List(parts) { index ->
        if (index < remainder) base + 1L else base
    }
}
// For 10000 paise across 3 parts: returns [3334L, 3333L, 3333L] -> Sum exactly 10000L!
Payments & Security Deep Dive
8. What is an Idempotency Key in payments, and how does `TransferBook` prevent double deductions on retries?

When a user taps "Pay ₹5,000", if the mobile network drops right as the bank is processing the debit, the client has no idea if the transfer succeeded or failed. If the client simply retries, the user could be debited twice!

Idempotency Key Mechanism: Before initiating a payment, the client generates a unique cryptographic UUID (idempotencyKey). The backend records all transactions indexed by this key. If a retry arrives with the same idempotency key, the backend returns the original confirmed transaction status instead of executing another debit.
Payments & Security Core
9. Explain the Luhn Algorithm for card validation and how PAN masking prevents compliance leaks.

Payment card numbers (13–19 digits) are verified using the Luhn (Mod-10) algorithm before transmitting to network switches:

  1. Traverse digits from right to left starting with the second-to-last digit.
  2. Double every second digit. If doubling results in a number > 9, subtract 9 (sum the digits).
  3. Sum all digits. If the total is divisible by 10 (sum % 10 == 0), the card is valid.

PAN Masking & Redaction: Under PCI-DSS compliance, full card numbers must never be written to logs, Room databases, or plain UI text. LedgerOne automatically passes card numbers through redactPans to mask them as **** **** **** 1234.

Payments & Security Deep Dive
10. How does Envelope Encryption work with the Android Keystore (TEE/StrongBox) for database security?

Encrypting a high-volume SQLite database directly inside the Android Keystore is impractical because hardware Keystore crypto operations are slow and cannot process streaming database I/O. LedgerOne uses Envelope Encryption:

  1. Key Encryption Key (KEK): A master 256-bit AES key is generated and sealed permanently inside the device's hardware-isolated Trusted Execution Environment (TEE) / StrongBox. The key material never leaves hardware.
  2. Database Encryption Key (DEK): A random 256-bit AES key is generated to encrypt the SQLCipher SQLite database.
  3. Envelope Sealing: The DEK is encrypted (wrapped) by the hardware KEK via AES-256-GCM and stored safely in private app files.
  4. Memory Zeroization: On app launch, the DEK is unwrapped, passed to SQLCipher, and the in-memory key buffer is immediately overwritten with zeros via PiiMasker.zeroize(byteArray).
Compose & UI Core
11. What is the fundamental difference between `remember` and `rememberSaveable` in Jetpack Compose?
  • remember { ... }: Preserves state across recompositions of the composable. However, if the Activity is recreated due to configuration changes (screen rotation, dark/light theme switch) or OS process death, the state is completely lost and resets to initial value.
  • rememberSaveable { ... }: Saves state inside Android's SavedStateRegistry (backed by Android OS Bundle). The state survives screen rotations AND OS process termination when the user temporarily leaves the app.
Rule of Thumb: Use rememberSaveable for all transient user inputs (search queries, form drafts, PIN inputs, step indices) so users never lose entered data when rotating their phone!
Compose & UI Advanced
12. When should you use `derivedStateOf` in Jetpack Compose, and what mistake do developers frequently make?

derivedStateOf is used when a composable state changes more frequently than the UI needs to update, allowing Compose to dampen unnecessary recompositions.

Classic Example (Scroll to Top Button): A LazyListState updates its scroll pixel offset on every single pixel of motion (60–120 times per second). We only care if the first visible item index is > 0:

// ✅ CORRECT: Recomposes ONLY when the boolean flips between true and false!
val showScrollToTop by remember {
    derivedStateOf { listState.firstVisibleItemIndex > 0 }
}
Common Mistake: Wrapping non-Compose snapshot state (like a plain Kotlin parameter) inside derivedStateOf. If the input is not a State<T>, derivedStateOf cannot observe it and will never invalidate!
Compose & UI Advanced
13. Why does Material 3 deprecate alpha blending (`copy(alpha = 0.6f)`) in favor of opaque tokens like `onSurfaceVariant`?
  1. GPU Frame Rate (120 FPS): Alpha blending forces the GPU's Skia rendering engine to allocate offscreen intermediate framebuffers to calculate transparency over backgrounds. Opaque colors (onSurfaceVariant) can be drawn in a single hardware pass.
  2. Guaranteed WCAG Contrast: Applying copy(alpha = 0.6f) causes unpredictable contrast variations over elevated or tinted surfaces. Pre-calculated opaque tokens guarantee compliant contrast (7.3:1 AA in Light, 8.4:1 AA in Dark).
  3. Design Consistency: Eliminates arbitrary magic alpha decimals (0.38f, 0.6f, 0.7f) scattered across codebases.
Compose & UI Core
14. What are RowScope and ColumnScope in Jetpack Compose, and what compile-time safety do they provide?

RowScope and ColumnScope are receiver scopes defined on the content lambdas of Row and Column. They supply scope-specific modifiers that are only valid in 1D linear layouts:

  • Modifier.weight(...): Distributes remaining horizontal width in a Row or remaining vertical height in a Column.
  • Cross-Axis Alignment: Modifier.align(...) takes Alignment.Vertical in a Row and Alignment.Horizontal in a Column.

Compile-Time Safety: You cannot accidentally call Modifier.weight() inside a Box or LazyColumn item—the Kotlin compiler prevents it at build time!

Room & Sync Core
15. How does LedgerOne implement an Offline-First architecture with Room and WorkManager?

In an offline-first architecture, the UI **never observes network endpoints directly**—it observes the local Room SQLite database as the single source of truth:

  1. Immediate Local Write: When a user takes an action, the record is immediately committed to Room with a sync flag: PENDING_CREATE or PENDING_UPDATE. The UI updates instantly.
  2. Background Sync (`WorkManager`): SyncWorker is registered with OS constraints (NetworkType.CONNECTED + BatteryNotLow).
  3. Reconciliation: When internet is restored, the worker pushes pending mutations to the remote API and flips local status to SYNCED.

16. How is accessibility (a11y) handled for masked balances in `MaskedAmount.kt`?

Visually, sensitive bank balances are masked with bullet characters: ₹ • • • • •. If a screen reader (TalkBack) simply reads the text, it will announce confusing gibberish: "Rupee, bullet, bullet, bullet".

LedgerOne solves this using custom Compose semantics:

Text(
    text = if (revealed) formattedAmount else "₹ • • • • •",
    modifier = Modifier.semantics {
        // TalkBack announces clear intent without exposing digits when hidden:
        contentDescription = if (revealed) spoken else "Balance hidden"
    }
)

IconButton(
    onClick = onToggle,
    modifier = Modifier.size(48.dp) // Minimum 48dp touch target
) {
    Icon(
        imageVector = if (revealed) Icons.Outlined.VisibilityOff else Icons.Outlined.Visibility,
        contentDescription = if (revealed) "Hide balance" else "Show balance"
    )
}
Accessibility Core
17. Why does LedgerOne use OpenType tabular numerals (`tnum`) for currency displays?

In standard proportional fonts, the digit 1 is significantly narrower than 8. When viewing vertical transaction lists or changing counters, columns jitter and wobble horizontally, making it difficult for users with dyslexia, vision impairments, or cognitive stress to scan finances.

LedgerOne configures the Inter font family with tabular figures (fontFeatureSettings = "tnum"). All numeric digits occupy identical advance widths, ensuring decimals and digits align in clean vertical columns.

Architecture Advanced
18. What is the Single Responsibility Principle (SRP) in Jetpack Compose UI components? Give an example from LedgerOne.

In Compose, the Single Responsibility Principle (SRP) dictates that every UI component should do exactly one thing and have one reason to change:

  • Separation of Files: Independent components are never lumped together into one file (e.g. LedgerOneButton.kt, LedgerOneText.kt, LedgerOneTextField.kt, and LedgerOneCard.kt are distinct files).
  • Scaffold vs TopBar: FeatureTopBar.kt is responsible solely for rendering title, subtitle, and back navigation. FeatureScaffold.kt is responsible solely for scaffolding the screen container, responsive width bounding (720dp), and content layout.
  • Decoupling State: Components are stateless presentation elements; state hoisting bubbles events up via lambdas (onClick, onValueChange).
Payments & Security Deep Dive
19. How does the Payment Finite State Machine (`PaymentStateMachine`) handle "In-Doubt" transactions?

A banking transaction flows through states: Form → AwaitingAuth → Submitting.

If network connection drops during Submitting, the client retries with exponential backoff (1s, 2s, 4s) using the same idempotencyKey. If all retries exhaust without server response, the transaction transitions to TransferStatus.IN_DOUBT (never Failed!):

  • The UI displays a "Check Status" reconciliation action rather than allowing immediate duplicate payment submission.
  • viewModel.reconcile() queries TransferBook.status(idempotencyKey). If the bank switch posted the debit before connection loss, the UI transitions cleanly to Success. If unrecorded, it safely enables re-attempt.
Accessibility Core
20. What are Android's minimum touch target standards, and how are they enforced in LedgerOne?

According to Material 3 and WCAG 2.1 guidelines, every interactive touch target must be at least 48 × 48 dp to prevent missed taps for users with motor tremors or one-handed usage:

  • LedgerOneButton: Full width × 52 dp height.
  • NumericKeypad: 3x4 keys × 60 dp (or 72 dp in large mode); backspace button is 56 × 56 dp.
  • MaskedAmount eye icon: Explicitly wrapped in a 48 × 48 dp IconButton.
  • Decorative icons explicitly specify contentDescription = null so screen readers do not waste time reading non-interactive graphics.
