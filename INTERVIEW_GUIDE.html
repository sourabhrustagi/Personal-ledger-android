Architecture Core
1. Explain LedgerOne's 3-tier multi-module architecture. Why are feature-to-feature dependencies strictly forbidden?

LedgerOne decomposes the application into three decoupled tiers:

  • :app (Application Shell): Wires Hilt dependency injection graphs, top-level navigation (LedgerNavHost), and background work dispatchers (WorkManager).
  • :feature:* (Feature Libraries): Encapsulates UI screens and ViewModels for distinct product domains (e.g., :feature:home, :feature:history, :feature:auth, :feature:account, :feature:promotions, :feature:scan).
  • :core:* (Core Shared Layer): Reusable domain models, design system, network abstractions, Room database, and testing utilities (e.g., :core:model, :core:designsystem, :core:database, :core:network).
Why forbid feature-to-feature dependencies? Allowing :feature:wallet to import :feature:ledger creates circular dependencies, tight coupling, and massive Gradle build bottlenecks. If two features need the same model, repository, or UI primitive, that code must be elevated to :core:*. This invariant is automatically verified by ModuleBoundaryTest on every CI build.

2. What are standalone feature demo apps (`:feature::demo`), and what technical problem do they solve?

Every feature module has a runnable companion application (e.g., :feature:home:demo, :feature:auth:demo). Feature libraries (com.android.library) cannot be launched as standalone APKs on devices. The demo app is a minimal com.android.application that embeds only that feature and mocks.

  • Instant Build Times: Building :app takes 30–60s due to full Room annotation processing, Hilt compilation, and all feature assets. Running :feature:account:demo compiles in 1–3 seconds.
  • Zero Navigational Friction: Developers and QA test deep edge cases (e.g., OTP timeouts, KYC rejection) immediately without logging in or navigating through the entire app funnel.
  • Independent Team Scalability: Feature teams can iterate without being blocked by regressions or merge conflicts in unrelated features.
Architecture Advanced
3. What is the Single Responsibility Principle (SRP) in Jetpack Compose UI components? Give examples from LedgerOne.

In Compose, the Single Responsibility Principle (SRP) dictates that every UI component should do exactly one thing and have one reason to change:

  • Separation of Files: Independent components are never lumped together into one file (e.g. LedgerOneButton.kt, LedgerOneText.kt, LedgerOneTextField.kt, and LedgerOneCard.kt are distinct files).
  • Scaffold vs TopBar: FeatureTopBar.kt is responsible solely for rendering title, subtitle, and back navigation. FeatureScaffold.kt is responsible solely for scaffolding the screen container, responsive width bounding (720dp), and content layout.
  • Decoupling SectionCard & SectionHeader: SectionHeader.kt is solely responsible for rendering labeled section divider rows. SectionCard.kt is solely responsible for container elevation, borders, padding, and grouping.
  • Decoupling State: Components are stateless presentation elements; state hoisting bubbles events up via lambdas (onClick, onValueChange).
Coroutines Deep Dive
4. Why must you NEVER swallow `CancellationException` in Kotlin coroutines? How can standard `runCatching` cause leaks?

In Kotlin, structured concurrency cancellation is cooperative and implemented under the hood by throwing CancellationException. When a coroutine scope cancels (e.g., user exits screen and viewModelScope terminates), a CancellationException cascades through the coroutine hierarchy.

The Danger of Swallowing CancellationException: If you catch Exception or Throwable without rethrowing CancellationException, the coroutine ignores the cancellation signal and continues running wasted work, leaking CPU cycles and network memory in the background! 
// ❌ INCORRECT: Swallows cancellation, preventing coroutine termination
try {
    api.submitTransfer(payload)
} catch (e: Exception) {
    Log.e(TAG, "Failed", e)
}

// ✅ CORRECT: Explicitly rethrows CancellationException
try {
    api.submitTransfer(payload)
} catch (e: CancellationException) {
    throw e
} catch (e: IOException) {
    Result.failure(e)
}

// ✅ CORRECT: runCatching with cancellation propagation
val result = runCatching { api.fetchStatement() }
    .onFailure { if (it is CancellationException) throw it }

5. Why should ViewModels expose read-only `StateFlow` via `WhileSubscribed(5_000)` instead of `Eagerly` or LiveData?

Converting upstream cold flows (e.g., Room database queries or location updates) into hot UI state in ViewModels is accomplished using stateIn:

val uiState: StateFlow<HomeUiState> = repository.observeDashboard()
    .map { HomeUiState.Success(it) }
    .stateIn(
        scope = viewModelScope,
        started = SharingStarted.WhileSubscribed(5_000),
        initialValue = HomeUiState.Loading
    )
  • Why `WhileSubscribed`? When the composable leaves the screen, upstream database/network flows automatically stop collecting, preserving battery and memory.
  • Why the 5,000ms (5-second) buffer? During configuration changes (screen rotation, multi-window split, dark mode toggle), the Activity destroys and recreates within ~200–500ms. The 5-second grace window keeps the upstream flow alive, avoiding expensive database restarts and screen flickering!
Financial Math Core
6. Why are currency amounts stored strictly as 64-bit `Long` minor units instead of `Double` or `Float`?

Floating-point types (Float and Double) adhere to the IEEE 754 binary standard, which represents fractions in base 2. Most decimal fractions (such as 0.10 or 0.01) cannot be represented precisely in binary:

// In Java/Kotlin:
println(0.1 + 0.2) // Prints: 0.30000000000000004!
The LedgerOne Rule: In financial software, a fraction of a cent discrepancy will fail bank reconciliations and audit compliance. LedgerOne stores all currency as integer Long values in **minor units** (paise for INR, cents for USD). Example: ₹1,245.50 is stored strictly as 124550L.
Financial Math Advanced
7. How does double-entry bookkeeping work in LedgerOne, and what invariants are enforced by `post()`?

Double-entry bookkeeping mandates that money never appears from or disappears into thin air; every debit from one account must be matched by an identical credit to another account:

fun post(legs: List<LedgerLeg>): Boolean {
    require(legs.isNotEmpty()) { "Transaction must contain at least one leg" }
    
    // Invariant 1: Every leg must be either debit or credit, never both or negative
    legs.forEach { leg ->
        require(leg.debitMinor >= 0L && leg.creditMinor >= 0L)
        require((leg.debitMinor == 0L) xor (leg.creditMinor == 0L))
    }
    
    // Invariant 2: Total debits must equal total credits
    val totalDebits = legs.sumOf { it.debitMinor }
    val totalCredits = legs.sumOf { it.creditMinor }
    return totalDebits == totalCredits
}

8. How does remainder-preserving expense splitting (`splitEvenly`) guarantee zero currency leakage?

When dividing ₹100.00 (10,000 paise) among 3 people, integer division yields 10000 / 3 = 3333 paise per person ($3333 \times 3 = 9999$). One paisa is lost as remainder! Ordinary systems drop the remainder or round up, causing financial drift.

splitEvenly solves this by distributing remainder paise one-by-one to the earliest participants:

fun splitEvenly(totalMinor: Long, parts: Int): List<Long> {
    require(parts > 0)
    val base = totalMinor / parts
    val remainder = (totalMinor % parts).toInt()
    
    return List(parts) { index ->
        if (index < remainder) base + 1L else base
    }
}
// For 10000 paise across 3 parts: returns [3334L, 3333L, 3333L] -> Sum exactly 10000L!
Financial Math Deep Dive
9. How are loan EMI and amortization schedules computed in LedgerOne (`emiMinor` and `amortize`)?

Monthly EMI is calculated using closed-form annuity compounding based on annual basis points ($1\% = 100\text{ bps}$):

fun emiMinor(principalMinor: Long, annualBps: Int, months: Int): Long {
    require(principalMinor > 0 && annualBps > 0 && months > 0)
    val monthlyRate = (annualBps.toDouble() / 10_000.0) / 12.0
    val factor = (1.0 + monthlyRate).pow(months.toDouble())
    val emi = principalMinor * (monthlyRate * factor) / (factor - 1.0)
    return emi.roundToLong()
}

Residual Balance Settlement in `amortize`: In the final month of the amortization schedule, rounding fractional paise could leave a residual balance of ₹0.02. LedgerOne dynamically clamps the final principal payment so the remaining balance settlements drop exactly to zero.

Payments & Security Deep Dive
10. What is an Idempotency Key in payments, and how does `TransferBook` prevent double deductions on retries?

When a user taps "Pay ₹5,000", if the mobile network drops right as the bank is processing the debit, the client has no idea if the transfer succeeded or failed. If the client simply retries, the user could be debited twice!

Idempotency Key Mechanism: Before initiating a payment, the client generates a unique cryptographic UUID (idempotencyKey). The backend records all transactions indexed by this key. If a retry arrives with the same idempotency key, the backend returns the original confirmed transaction status instead of executing another debit.
Payments & Security Core
11. Explain the Luhn Algorithm for card validation and how PAN masking prevents compliance leaks.

Payment card numbers (13–19 digits) are verified using the Luhn (Mod-10) algorithm before transmitting to network switches:

  1. Traverse digits from right to left starting with the second-to-last digit.
  2. Double every second digit. If doubling results in a number > 9, subtract 9 (sum the digits).
  3. Sum all digits. If the total is divisible by 10 (sum % 10 == 0), the card is valid.

PAN Masking & Redaction: Under PCI-DSS compliance, full card numbers must never be written to logs, Room databases, or plain UI text. LedgerOne automatically passes card numbers through redactPans to mask them as **** **** **** 1234.

Payments & Security Deep Dive
12. How does Envelope Encryption work with the Android Keystore (TEE/StrongBox) for database security?

Encrypting a high-volume SQLite database directly inside the Android Keystore is impractical because hardware Keystore crypto operations are slow and cannot process streaming database I/O. LedgerOne uses Envelope Encryption:

  1. Key Encryption Key (KEK): A master 256-bit AES key is generated and sealed permanently inside the device's hardware-isolated Trusted Execution Environment (TEE) / StrongBox. The key material never leaves hardware.
  2. Database Encryption Key (DEK): A random 256-bit AES key is generated to encrypt the SQLCipher SQLite database.
  3. Envelope Sealing: The DEK is encrypted (wrapped) by the hardware KEK via AES-256-GCM and stored safely in private app files.
  4. Memory Zeroization: On app launch, the DEK is unwrapped, passed to SQLCipher, and the in-memory key buffer is immediately overwritten with zeros via PiiMasker.zeroize(byteArray).
Payments & Security Deep Dive
13. What is Privacy-Preserving Blind Indexing, and how does it allow exact-match queries without decrypting the database?

High-risk customer records (such as Social Security Numbers, PANs, or deed titles) are encrypted using non-deterministic AES-256-GCM (random 12-byte IVs). Because ciphertext changes every time for identical plaintext, you cannot perform SQLite WHERE ssn = ? lookups without decrypting the whole database!

The Blind Index Solution (computeBlindIndex): The system computes a deterministic HMAC-SHA256 hash over the normalized plaintext using a dedicated HMAC key stored in the Keystore. The database stores the encrypted ciphertext AND the blind index hash. Searches match against the blind index hash, enabling instant indexed queries with zero PII exposure!
Payments & Security Deep Dive
14. How does the Payment Finite State Machine (`PaymentStateMachine`) handle "In-Doubt" transactions?

A banking transaction flows through states: Form → AwaitingAuth → Submitting.

If network connection drops during Submitting, the client retries with exponential backoff (1s, 2s, 4s) using the same idempotencyKey. If all retries exhaust without server response, the transaction transitions to TransferStatus.IN_DOUBT (never Failed!):

  • The UI displays a "Check Status" reconciliation action rather than allowing immediate duplicate payment submission.
  • viewModel.reconcile() queries TransferBook.status(idempotencyKey). If the bank switch posted the debit before connection loss, the UI transitions cleanly to Success. If unrecorded, it safely enables re-attempt.
Compose & UI Core
15. What is the fundamental difference between `remember` and `rememberSaveable` in Jetpack Compose?
  • remember { ... }: Preserves state across recompositions of the composable. However, if the Activity is recreated due to configuration changes (screen rotation, dark/light theme switch) or OS process death, the state is completely lost and resets to initial value.
  • rememberSaveable { ... }: Saves state inside Android's SavedStateRegistry (backed by Android OS Bundle). The state survives screen rotations AND OS process termination when the user temporarily leaves the app.
Rule of Thumb: Use rememberSaveable for all transient user inputs (search queries, form drafts, PIN inputs, step indices) so users never lose entered data when rotating their phone!
Compose & UI Advanced
16. When should you use `derivedStateOf` in Jetpack Compose, and what mistake do developers frequently make?

derivedStateOf is used when a composable state changes more frequently than the UI needs to update, allowing Compose to dampen unnecessary recompositions.

Classic Example (Scroll to Top Button): A LazyListState updates its scroll pixel offset on every single pixel of motion (60–120 times per second). We only care if the first visible item index is > 0:

// ✅ CORRECT: Recomposes ONLY when the boolean flips between true and false!
val showScrollToTop by remember {
    derivedStateOf { listState.firstVisibleItemIndex > 0 }
}
Common Mistake: Wrapping non-Compose snapshot state (like a plain Kotlin parameter) inside derivedStateOf. If the input is not a State<T>, derivedStateOf cannot observe it and will never invalidate!

18. Why does Material 3 deprecate alpha blending (`copy(alpha = 0.6f)`) in favor of opaque tokens like `onSurfaceVariant`?
  1. GPU Frame Rate (120 FPS): Alpha blending forces the GPU's Skia rendering engine to allocate offscreen intermediate framebuffers to calculate transparency over backgrounds. Opaque colors (onSurfaceVariant) can be drawn in a single hardware pass.
  2. Guaranteed WCAG Contrast: Applying copy(alpha = 0.6f) causes unpredictable contrast variations over elevated or tinted surfaces. Pre-calculated opaque tokens guarantee compliant contrast (7.3:1 AA in Light, 8.4:1 AA in Dark).
  3. Design Consistency: Eliminates arbitrary magic alpha decimals (0.38f, 0.6f, 0.7f) scattered across codebases.
Compose & UI Core
19. What are RowScope and ColumnScope in Jetpack Compose, and what compile-time safety do they provide?

RowScope and ColumnScope are receiver scopes defined on the content lambdas of Row and Column. They supply scope-specific modifiers that are only valid in 1D linear layouts:

  • Modifier.weight(...): Distributes remaining horizontal width in a Row or remaining vertical height in a Column.
  • Cross-Axis Alignment: Modifier.align(...) takes Alignment.Vertical in a Row and Alignment.Horizontal in a Column.

Compile-Time Safety: You cannot accidentally call Modifier.weight() inside a Box or LazyColumn item—the Kotlin compiler prevents it at build time!

Compose & UI Advanced
20. How does `Modifier.weight` work under the hood, and what is the difference between `fill = true` and `fill = false`?

Compose measures weighted items using a two-pass measurement algorithm:

  1. Measure all unweighted children first to determine their intrinsic fixed size.
  2. Calculate free space: $\text{FreeSpace} = \text{TotalSpace} - \sum \text{UnweightedSizes}$.
  3. Allocate remaining free space proportionally among weighted children: $\text{Size}_i = \text{FreeSpace} \times \frac{\text{weight}_i}{\sum \text{weights}}$.
The `fill` Parameter:
  • fill = true (Default): Forces the child to expand to exactly the allocated size, even if content is smaller.
  • fill = false: Sets a proportional maximum size ceiling. If content is small, the child stays at its intrinsic size without stretching (e.g., wrapping a short LazyColumn inside a SectionCard).
Compose & UI Deep Dive
21. How do you defer state reads in Compose to skip the Composition and Layout phases during 120 FPS animations?

Compose has three phases: 1. Composition → 2. Layout → 3. Draw.

Reading state in Phase 1 causes the entire composable to recompose on every frame change. By using lambda-based modifiers, state reads are deferred to Phase 2 (Layout) or Phase 3 (Draw):

// ❌ BAD: Reads scroll offset in Composition phase -> Triggers 120 recompositions/sec!
Box(Modifier.offset(y = scrollState.value.dp))

// ✅ GOOD: Lambda deferral reads state during Layout phase -> Composition is SKIPPED!
Box(Modifier.offset { IntOffset(0, scrollState.value) })

// ✅ BEST for colors/alpha: Reads state during Draw phase -> Composition AND Layout SKIPPED!
Box(Modifier.drawBehind { drawRect(color = dynamicColorState.value) })
Compose & UI Advanced
22. Why are `key` and `contentType` crucial in `LazyColumn` for preventing frame drops and recomposition spikes?
  • Stable Keys (`key = { it.id }`): By default, Compose uses item indices as keys. Inserting or deleting an item shifts all subsequent indices, forcing Compose to recompose every visible item in the list. Providing a stable domain ID allows Compose to recognize that items only shifted positions, animating moves with zero recompositions.
  • Content Types (`contentType = "passbook_row"`): When items scroll offscreen, Compose reuses matching composition slots for newly visible items of the same contentType (similar to RecyclerView view-type recycling), avoiding expensive slot reallocation.
Room & Sync Core
23. How does LedgerOne implement an Offline-First architecture with Room and WorkManager?

In an offline-first architecture, the UI **never observes network endpoints directly**—it observes the local Room SQLite database as the single source of truth:

  1. Immediate Local Write: When a user takes an action, the record is immediately committed to Room with a sync flag: PENDING_CREATE or PENDING_UPDATE. The UI updates instantly.
  2. Background Sync (`WorkManager`): SyncWorker is registered with OS constraints (NetworkType.CONNECTED + BatteryNotLow).
  3. Reconciliation: When internet is restored, the worker pushes pending mutations to the remote API and flips local status to SYNCED.

37. How does LedgerOne integrate `BiometricPrompt` with hardware-backed Keystore `CryptoObject` to authorize high-value transactions securely?

Rather than relying on vulnerable boolean callbacks (onAuthenticationSucceeded), which can be manipulated by instrumentation hooks (Frida/Xposed) on rooted devices, LedgerOne ties biometric authorization directly to cryptographic hardware unlocking:

  • Hardware-Bound Key Specification: Generates an AES-256 or RSA key inside the Android Keystore (StrongBox Keymaster / TEE) configured with setUserAuthenticationRequired(true) and setUserAuthenticationParameters(0, KeyProperties.AUTH_BIOMETRIC_STRONG).
  • BiometricPrompt.CryptoObject: Prior to displaying the system prompt, the app initializes a Cipher in ENCRYPT_MODE or a Signature object using the protected key. The Keystore refuses to initialize the cipher without user presence.
  • Hardware-Verified Decryption: Passing BiometricPrompt.CryptoObject(cipher) into prompt.authenticate() guarantees that the Cipher is cryptographically unlocked ONLY when the Secure Element / TEE verifies the user's authentic biometric signature (Fingerprint or 3D Face Unlock).
  • Tamper-Proof Transaction Signing: The transaction payload (amount, payee VPA, timestamp, idempotency key) is signed by this authenticated cipher, providing undeniable cryptographic non-repudiation.

Cryptographic Security Deep Dive
39. Why is Nonce / IV reuse in AES-GCM encryption catastrophic, and how does LedgerOne prevent keystream leakage during database column encryption?
Catastrophic Keystream Leakage: In AES-GCM (Galois/Counter Mode), repeating a Nonce/IV with the same master key completely destroys confidentiality and message authenticity.

Under AES-GCM, the ciphertext $C$ is computed by XORing plaintext $P$ with a keystream $K$ generated from the key and counter block ($C_1 = P_1 \oplus K$, $C_2 = P_2 \oplus K$).

  • Plaintext Exposure: If the IV is reused across two records, XORing the ciphertexts yields the XOR of the plaintexts: $C_1 \oplus C_2 = P_1 \oplus P_2$. Any known plaintext prefix (e.g. standard JSON keys or card prefixes) immediately recovers the other message's contents.
  • GHASH Key Recovery: Furthermore, nonce reuse in GCM allows an attacker to mathematically solve for the universal GHASH authentication key $H$, allowing the attacker to forge arbitrary valid ciphertexts and inject fraudulent ledger entries.
  • LedgerOne Implementation: LedgerOne strictly generates a fresh 12-byte (96-bit) cryptographically strong random IV using SecureRandom for every single encryption call. The IV is prepended to the ciphertext and stored as: [12-byte IV] + [Ciphertext] + [16-byte GCM Authentication Tag].
Staff Engineering & Leadership Deep Dive
40. Describe how you handle high-pressure business/product requests that introduce severe architectural and security risks (The "Zero-Friction Offline Auto-Pay" trade-off).

This is a real-world Staff Engineer leadership case study from the LedgerOne architecture:

  • The Business Request: Product management requested a "Zero-Friction Offline Auto-Pay" feature: enabling users in poor network environments (subways, rural bazaars) to complete recurring merchant payments offline without PIN confirmation, queuing transactions locally to sync whenever connectivity returned.
  • The Hidden Catastrophes:
    1. Double-Spending & Account Overdraft: A user could spend ₹5,000 at Merchant A offline, and simultaneously spend ₹5,000 at Merchant B online, creating an irrecoverable ledger deficit.
    2. Replay & Relay Attacks: A malicious merchant terminal could capture the offline packet and replay it multiple times to drain the user's funds.
    3. Physical Device Theft: If a phone was stolen, an attacker could make infinite offline purchases without triggering biometric or PIN challenges.
  • Stakeholder Communication Strategy: Rather than saying "no" outright, the engineering lead translated technical failure modes into commercial business metrics: calculated default rates, regulatory non-compliance fines, and chargeback dispute liability.
  • The Win-Win Architectural Solution: "Pre-Authorized Signed Intent with 15-Minute TTL". The user pre-authorizes an exact expenditure amount while online using biometric authentication. The app signs a hardware-backed cryptographic voucher containing an idempotency key, recipient VPA, maximum amount, and a strict 15-minute Time-To-Live (TTL). When offline, this signed voucher is verified by the merchant terminal without overdraft risk or indefinite replay exposure.
Testing & Quality Advanced
41. How do you test asynchronous Kotlin Flows and state transitions deterministically without using flaky `Thread.sleep()` or arbitrary coroutine `delay()`?

LedgerOne uses Square's Turbine library combined with kotlinx-coroutines-test (runTest) to test cold and hot asynchronous flows deterministically:

@Test
fun `transfers flow transitions from Loading to Success with transaction items`() = runTest {
    val repository = FakeLedgerRepository()
    val viewModel = LedgerViewModel(repository)

    viewModel.uiState.test {
        // Assert initial state emitted upon subscription
        assertThat(awaitItem()).isEqualTo(LedgerUiState.Loading)

        // Trigger action
        viewModel.loadTransactions()

        // Assert subsequent emission
        val successState = awaitItem() as LedgerUiState.Success
        assertThat(successState.items).hasSize(3)

        // Verify no unexpected emissions or leaks
        expectNoEvents()
    }
}
  • Virtual Time Control: runTest virtualizes the coroutine clock. Calls like delay(10_000) complete instantaneously in the test environment, eliminating flaky timeouts on CI machines.
  • Deterministic Item Consumption: awaitItem() suspends until the flow emits, capturing exceptions immediately if the coroutine crashes or emits unexpected events.

App Distribution & Updates Advanced
43. How does LedgerOne handle mandatory security patches and breaking API migrations using the Force Update Engine (`:feature:update`)?

The :feature:update module provides robust client version management using the Google Play Core In-App Update API paired with backend configuration fallback:

  • Immediate (Blocking) Updates: Used when a breaking database schema migration or critical security vulnerability occurs. The app queries the configuration endpoint on cold launch. If currentVersionCode < minSupportedVersionCode, the app launches AppUpdateType.IMMEDIATE. A fullscreen, non-cancellable UI blocks interaction with the rest of the app, routing the user directly into Google Play's update flow.
  • Flexible (Background) Updates: For non-breaking improvements, the app requests AppUpdateType.FLEXIBLE. The update is downloaded silently in the background while the user continues interacting with the ledger. Once downloaded, a Snackbar notifies the user: "Update ready. Restart to finish installation."
  • OEM / Sideload Fallback: If Google Play Services is unavailable on the device (e.g. custom OEM builds or Chinese market variants), the module falls back to launching an explicit Market intent (market://details?id=com.ledger.personal) or downloading from a secure enterprise distribution endpoint.
